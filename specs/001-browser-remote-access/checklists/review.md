# 需求质量清单：DSHAnywhere 浏览器远程接入

**用途**：在进入 tasks/实现前，审查本特性**需求的写法**是否完整、清晰、一致、可度量、覆盖充分。本清单检验的是规格与契约的文本质量，不是实现是否可用。
**创建时间**：2026-11-04
**对应特性**：[spec.md](../spec.md) · [plan.md](../plan.md) · [contracts/](../contracts/) · [data-model.md](../data-model.md)

**审查归属**：本清单由审查者拥有。`[x]` 表示审查者确认该条**需求质量判据**已被满足，不代表实现完成。
**标记语义**：`[ ]` 待审查或仍需澄清；`[x]` 已审查通过。`$speckit-implement` 读取勾选状态作为门禁，但不得修改标记。

## 安全与隐私

- [ ] CHK001 是否给出凭证强度的可验证定量定义（位数/字节数/编码方式），而非仅"高熵"一词？ [Clarity, Spec §FR-015]
- [ ] CHK002 是否形成完整的威胁模型（攻击者身份、攻击面、被排除的威胁），并与各条安全需求对应？ [Completeness, Gap]
  - → 已补：spec 新增「威胁模型」章节（对手表 + 明确不防御边界 + 与需求编号的对应规则）
- [ ] CHK003 泄露止损路径（轮换、撤销）是否同时具备时限、可验证判据与不受影响的对照项？ [Measurability, Spec §FR-016~FR-018]
- [ ] CHK004 是否明确了凭证"不得出现"的全部位置边界（插件日志、中转日志、错误信息、监控上报、界面），且对中转侧同样成立？ [Completeness, Spec §FR-015, §FR-021]
- [ ] CHK005 浏览器侧凭证的存储与传输约束是否可被外部检查（不可被脚本读取、跨站不携带、加密传输）？ [Clarity, Spec §FR-020]
- [ ] CHK006 对无效/过期/已撤销凭证，"统一措辞"的判定标准是否写明（哪些情况必须同文案、哪些可区分）？ [Consistency, Spec §FR-004, §FR-019]
- [ ] CHK007 "远程与本地完全等价"是否给出可验证的口径（用什么操作、看什么结果判定等价）？ [Clarity, Spec §FR-011]
- [ ] CHK008 计划中所有接触 DSH 内部的点是否都被映射到 Constitution I 的合规结论（无遗漏的"顺手改动"）？ [Consistency, Constitution §I, plan Constitution Check]
- [ ] CHK009 面向使用者的安全动作是否定义了失败路径（撤销最后一台设备、并发轮换、撤销正在进行会话的设备）？ [Edge Case, Spec §FR-018]
- [ ] CHK010 是否要求凭证存储最小化（只存摘要）并限定明文出现次数，且该要求可从数据模型验证？ [Completeness, data-model §Device, §CapabilityLink]

## 场景与边界覆盖

- [ ] CHK024 边界情况清单中的每一项，是否都能追到某条功能需求或被明确列为范围外？ [Coverage, Spec §边界情况]
- [ ] CHK025 电脑休眠/唤醒、桌面端退出、中转被删除三种中断的用户可见结果是否互不矛盾？ [Consistency, Spec §FR-013]
- [ ] CHK026 "大体积输出仍可用"是否量化了"大"（体积或条数），否则如何判定通过？ [Clarity, Spec §边界情况]
  - → 已补：边界情况改为「数十 MB 量级，上限以中转契约的 25 MiB 为准」，超限即明确失败可重试
- [ ] CHK027 是否定义了同一能力链接被两次并发扫描时的获胜规则与失败方提示？ [Gap]
  - → 已补：FR-004 增加"同一链接只能被成功消费一次，同时到达的第二个请求按无效处理"；边界情况增加并发扫描场景
- [ ] CHK028 时钟偏差场景是否给出了明确判定方向（拒绝而非误放行），并说明判定依据？ [Completeness, Spec §边界情况]
- [ ] CHK029 是否定义了"配对中途中转断开"这种跨场景失败的用户可见结果？ [Coverage, Gap]
  - → 已补：边界情况增加「配对中断 → 提示连接已中断、链接视为已消费、需重新生成」
